# تحویل فایل موجود ویندوز؛ بدون بازسازی

فایل فعلی `release/Hamdars-1.0.0-Windows-x64.exe` سالم است: **۹۹٬۹۴۴٬۴۲۹ بایت**، حدود **۹۹٫۹۴ مگابایت / ۹۵٫۳۱ MiB**. خروجی **قابل‌حمل (portable)** است؛ نصاب مرحله‌ای نیست. بستهٔ NSIS یک اجراکننده ۳۲ بیتی دارد، اما برنامهٔ واقعی داخل `app-64.7z`، **PE32+ x64 با machine=0x8664** است. آرشیو بیرونی و داخلی با بررسی CRC و بازکردن کامل تأیید شده‌اند. فایل کاربران در بسته وجود ندارد.

SHA256:

```text
b0d2826c0d488bc5326d8af729c97da90796977d0fa7690f163bb7b176117d19
```

این فایل در همین گفت‌وگو به‌عنوان پیوست آپلود نشده است. ابزار موجود برای فایل فقط دریافت فایل‌های آپلودشده را پشتیبانی می‌کند؛ ابزار ایجاد پیوست یا لینک میزبانی‌شده در این محیط موجود نیست. مسیر `/workspace/...` لینک دانلود عمومی نیست. اسکریپت‌های زیر برای انتقال همین فایل موجود آماده‌اند و هیچ دستور build، npm install یا بسته‌بندی اجرا نمی‌کنند.

## ۱. بررسی محلی و بدون شبکه

```bash
cd /workspace/apps
node scripts/release-existing-windows.mjs --dry-run
```

این دستور وجود، حجم، هدر اجرایی و SHA256 فایل را با `distribution/windows-existing.json` و `SHA256SUMS.txt` تطبیق می‌دهد. بررسی کامل آرشیو و x64 بودن فایل واقعی قبلاً انجام شده و در `release/VERIFICATION.txt` ثبت شده است. فایل و checksum در جریان آماده‌سازی انتشار تغییر نکرده‌اند.

## ۲. بارگذاری همین فایل در GitHub Release

پیش‌نیازها:

- دسترسی HTTPS این محیط به `api.github.com` و `uploads.github.com`. پیشنهاد افزودن این دو دامنه قبلاً در پیش‌نویس تنظیمات محیط ذخیره شده است؛ ذخیره پیش‌نویس به‌تنهایی شبکه در حال اجرا را تغییر نمی‌دهد. دسترسی فعلی هنوز با خطای `CONNECT tunnel failed, response 403` مسدود است.
- اتصال موجود گیت‌هاب باید برای API و نوشتن در مخزن مجوز داشته باشد. وجود متغیر `GH_TOKEN` یا موفقیت خواندن Git این مجوز را ثابت نمی‌کند؛ پس از رفع مسدودی باید خود عملیات دوباره بررسی شود. مقدار هیچ توکنی را در چت یا فایل کد ننویسید.
- مخزن باید حداقل یک commit داشته باشد. مخزن `h4d2admin-art/apps` در آخرین بررسی هیچ ref نداشت. گزینهٔ صریح `--initialize-empty-repo` در صورت تأیید خالی بودن توسط API، فقط یک فایل توضیح انتشار اولیه را ایجاد می‌کند؛ کد برنامه یا پایگاه داده را خودکار push نمی‌کند.

ابتدا پیش‌نویس انتشار را آماده کنید؛ این مرحله انتشار عمومی نیست:

```bash
node --use-env-proxy scripts/release-existing-windows.mjs \
  --repo h4d2admin-art/apps --tag v1.0.0 --initialize-empty-repo
```

اسکریپت ابتدا فایل را بررسی می‌کند، سپس draft می‌سازد و **همان EXE موجود** و `SHA256SUMS.txt` را بارگذاری می‌کند. فایل قبلی متفاوت را حذف یا جایگزین نمی‌کند. انتشار نهایی پیش‌فرض نیست. خروجی اسکریپت فقط پس از پاسخ موفق گیت‌هاب، آدرس واقعی صفحه draft را نشان می‌دهد. draft فقط برای افرادی با دسترسی لازم به مخزن قابل مشاهده است.

برای انتشار، فایل‌های draft را در گیت‌هاب بررسی و **Publish release** را بزنید. یا پس از تصمیم به انتشار، دستور را با `--publish` اجرا کنید؛ انتشار فقط پس از تأیید بارگذاری هر دو فایل انجام می‌شود. در مخزن خصوصی، دریافت فایل به ورود و دسترسی گیت‌هاب نیاز دارد؛ این اسکریپت مخزن را عمومی نمی‌کند.

تا وقتی آپلود و انتشار موفق نشده است، هیچ URL فرضی را لینک دانلود فعال در نظر نگیرید.

## ۳. دریافت همان فایل از GitHub Actions

گردش‌کار `.github/workflows/windows-existing-artifact.yml` آماده است. این فایل و `distribution/windows-existing.json` باید در شاخه پیش‌فرض مخزن قرار بگیرند؛ شاخه پیش‌فرض نباید با فرض وجود `main` ساخته یا بازنویسی شود. این مرحله هنوز push نشده است.

پس از انتشار Release بالا:

1. در مخزن، **Actions → Download existing Hamdars Windows EXE → Run workflow** را باز کنید و تگ `v1.0.0` را بدهید. برای اجرای خودکار با رویداد انتشار، workflow باید از قبل در revision مربوط به رویداد موجود باشد. اگر draft با commit اولیهٔ مخزن خالی ساخته شده و workflow را بعداً اضافه کرده‌اید، از همین مسیر دستی استفاده کنید؛ اجرای خودکار تضمین نمی‌شود.
2. گردش‌کار، EXE و checksum را از Release می‌گیرد، SHA256 و CRC آرشیو و PE32+ x64 بودن برنامه داخل آن را روی runner ویندوز بررسی می‌کند.
3. در صفحه اجرای موفق، بخش **Artifacts**، فایل `Hamdars-1.0.0-Windows-x64-existing` را دانلود کنید. فایل ZIP دریافتی شامل EXE دست‌نخورده و checksum است. ورود به گیت‌هاب و مجوز مخزن ممکن است لازم باشد. ماندگاری artifact برابر ۳۰ روز است؛ فایل Release ماندگارتر است.

این مسیر Actions آینهٔ فایل Release موجود است و مسیر ساخت تازه نیست. اگر Release موجود نباشد یا فایل خراب باشد، اجرا با خطا متوقف می‌شود؛ برنامه را خودکار دوباره نمی‌سازد.

آزمون‌های ابزار تحویل (بدون شبکه، انتشار یا بازسازی):

```bash
node --test tests/windows-delivery.test.mjs
```

این آزمون‌ها فایل واقعی موجود و حالت‌های draft، انتشار صریح پس از بارگذاری، خرابی فایل، تداخل فایل موجود، مقصد آپلود غیرمجاز و مقداردهی صریح مخزن خالی را بررسی می‌کنند. آزمون‌های API از پاسخ‌های شبیه‌سازی‌شده استفاده می‌کنند؛ اجرای موفق آن‌ها به معنی آپلود واقعی یا اجرای واقعی GitHub Actions نیست.
